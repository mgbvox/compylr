Where compylr Loses

Three of fifteen demo workloads run slower compiled than interpreted. They are not outliers — they are three separate systemic costs in the generated code, and each one was reproduced, patched by hand, and re-measured.

The baseline

make demo SCALE=4, compiled against interpreted, best of five batches. The scale is logarithmic and the hairline is parity — anything left of it is a workload the compiler made worse.

Seven ways to get it back

Ordered cheapest first, which is also roughly least-invasive first. Every delta below was measured by hand-patching demo/.compylr/crate/ and rebuilding; the crate has since been restored, and no compiler source changed on this branch.

1

The generated crate has no [profile.release] at all

10–25% across the board one config line +3s build

The bridge writes a manifest with [package], [lib] and [dependencies] — and nothing else. So every user's crate builds at codegen-units = 16, lto = false.

That matters more here than in most crates. compat.rs and generated.rs are separate modules, and at sixteen codegen units the runtime helpers routinely land in a different unit from their only caller — so py_add, py_index and resolve_index are not inlined. Since every arithmetic operation in the subset is a trait call by design, that is a great many un-inlined calls.

2

x = x + y on a string is quadratic where CPython's is not

4.1x on text.joined emitter peephole

Every word of text.joined currently emits:

out = PyAdd::py_add(&(PyAdd::py_add(&(out), &(separator))?), &(word))?;

PyAdd for String allocates a fresh String and copies both sides — so that is two full copies of the accumulator per iteration. CPython special-cases s = s + t when the target holds the only reference and resizes in place, which makes the interpreted version amortized linear. Compiling this loop currently makes it asymptotically worse.

Replacing the two lines with push_str took the row from 0.9x to 3.8x:

workloadbeforeaftergain
text.joined343.76us83.08us4.1x

The shape of the fix: recognise an accumulator that reads itself — Assign { name, value: Binary { Add, left: Name(name), .. } } — and emit an in-place update. Keep it type-directed the way everything else is, through a PyAddAssign trait: String gets push_str, i64 gets the checked add it already has. The backend still never learns the operand's type.

joined's own docstring says it is quadratic because each + builds a new string. True of the algorithm — but the generated code is quadratic with a constant factor of two on top, and that part is ours.

3

Every mapping and set uses SipHash

up to 1.93x turns a loss into a win exposes a latent bug

rust_ty emits bare HashMap/HashSet, so generated code inherits RandomState. SipHash is the right default for keys arriving over a network and the wrong one for keys coming from the user's own program. CPython hashes small ints to themselves and caches a string's hash in the string object — so on dict[int, ...] compylr does strictly more work per lookup than the interpreter it is meant to beat.

A self-contained FxHasher in runtime.rs — about forty lines, no external crate, in keeping with that file's self-contained rule:

workloadbeforeaftergain
graphs.bfs_distances159.36us82.49us1.93x
graphs.topological_order421.48us271.33us1.55x
text.word_count189.51us166.44us1.14x

bfs_distances goes from 0.7x to 1.4x — from losing to winning.

This surfaced a latent design bug. The runtime's impls read impl<K, V> PyIndexable<K> for HashMap<K, V>, which silently pins S = RandomState. The hasher is not currently a choice — it is baked into ten trait impls. Making them generic over S is mechanical and worth doing whatever hasher wins, and once it is generic the hasher becomes a natural TargetOption beside unchecked-arithmetic.

One knock-on: HashMap::from([...]) exists only for RandomState, so dict and set literals must emit FromIterator instead. Trivial — but an emitter change, not only a runtime one.

4

for x in xs clones every element

1.49x on a trivial loop needs blanket impls first

PyIterate for Vec<T> is self.iter().cloned(), and collection_loop binds the clone into an owned local. For Vec<i64> that is free. For Vec<String> it is an allocation and a copy per element, per loop.

text.total_length is the cleanest measurement available — its body is one len() per word:

N = 2000as generatedby referencegain
text.total_length88.52us59.43us1.49x

The loop variable is only read there, and lowering already computes the answer: is_assigned runs a few lines above purely to decide mut. The same call says whether a borrow would do.

What blocks it: the runtime traits are implemented on owned types only, so a &String loop variable fails to satisfy PyLen — I hit exactly that compile error making the patch. It needs blanket impl<T: PyLen + ?Sized> PyLen for &T and the same for PyContains and PyAdd. That is the real work; the emitter change is three lines.

5

A returned local is deep-copied on the way out

25 of 25 sites in the demo scales with result size

Stmt::Return routes through emit_expr, which clones any non-Copy Expr::Name. So return counts emits Ok(counts.clone()) — a full deep copy of the collection, immediately before the function ends and the original is dropped.

Removing all twenty-five in the demo compiled clean and changed no answer. The gain is modest here (topological_order 271us → 243us) because the demo's returned collections are small next to its loops — but it is a pure win and it grows with result size.

Not unconditionally sound. for v in xs: return xs would move out of something the loop borrows. Restricting the move to tail position — the emit_body tail branch, which is the last statement at depth zero and so cannot sit inside any loop — is trivially safe and covered all 25 sites.

Neighbouring waste, same emitter: d[k] = v emits let __compylr_index = k.clone(); and then py_set does insert(key.clone(), value). Two allocations per dict write where one is needed.

6

The boundary is O(n) per collection argument — and it is the ceiling for everything above

16x slower on binary_search design change

A collection parameter is converted element by element on every call. Timed at a fixed N = 2000:

probe (N = 2000)compiledinterpretedverdict
binary_search(list[int]) — O(log n) body8.12us0.49us16x slower
is_sorted(list[int]) — O(n) body8.61us64.55us7.5x faster
mean(list[float]) — O(n) body9.83us16.59us1.7x faster
total_length(list[str]) — O(n) body83.58us32.33us2.6x slower
copy_of(list[int]) — in and out28.43us16.15us1.8x slower

Per element, roughly:

  • list[int] in: ~4 ns — cheap, no allocation.
  • returning a list[int]: ~10 ns — a fresh PyLong each.
  • list[str] in: ~42 ns — a Rust String allocated and UTF-8 copied per element. Ten times the int cost, and the whole reason every list[str] workload in the demo loses.

binary_search is the sharpest statement of the problem: compiling it converts 2000 elements in order to do eleven comparisons, turning an O(log n) algorithm into an O(n) one and losing to the interpreter by 16x. No amount of codegen quality fixes that.

Directions, roughly in cost order:

  • Borrow read-only string parameters. PyO3 can hand back the interned UTF-8 without allocating (Cow<'_, str>, or a borrowed &str). This alone removes the 10x str penalty — and read-only is already the subset's rule, since mutating a parameter is a rejected program. The compiler knows.
  • Stop converting per call. An instance behind #[pyclass] already crosses once and stays Rust-side; that is why an attribute can be a cache. A compylr-owned list held across calls would extend the same trick to free functions, so a pipeline of compiled calls converts once rather than once per hop.
  • The buffer protocol for numeric lists, where the caller can supply array or memoryview.
  • Cheapest of all — say so. A collection parameter costs O(n) even when the body is O(1). That is written down nowhere, and demo/README.md reads as though compiled is always at least as fast. One paragraph would stop the next person losing an afternoon.
7

Smaller runtime items, worth one sweep

runtime.rs 2.7x when combined
  • py_index bounds-checks twice. resolve_index proves resolved < length, then items[resolved] checks again; the i64/usize round trip likely defeats LLVM's elision. Fixable without unsafe.
  • py_str_len under CodePoints is O(n) per call. chars().count() decodes the whole string every time len(s) is evaluated. An is_ascii() fast path returning len() is exact when it hits, and ASCII is the common case.
  • Three hash lookups per d[k] = d[k] + 1. k in d, then d[k], then the write. The entry API does it in one.
  • No with_capacity anywhere. vec![] then push in a loop whose trip count is often a range bound already in hand.

A hand-written ideal word_count body — borrow-iterate, one entry-style lookup, no return clone — runs in 62.31us against 167.27us as generated. That is 2.7x, and level with CPython's 56us. Everything left over is the boundary from item 6.

A measurement problem to fix first

sorting.merge_sort returned 202, 277, 235, 256, 264 and 160 us across runs of binaries that were in some cases byte-identical. It is recursive and allocation-heavy, and best-of-five-batches does not stabilise it. Any conclusion drawn from that row today is noise — I discarded my own apparent "regression" on it for exactly that reason.

Before optimising against this benchmark, it is worth having the harness report a spread rather than a single best, so that a real 10% regression is distinguishable from this.

Suggested order, and what it adds up to

Items 1, 2 and 5 are self-contained, testable, and touch no semantics — one change each. Item 3 is a small runtime refactor with a real payoff and an existing latent bug to fix on the way. Item 4 needs the blanket impls first. Item 6 is a design change and deserves its own OpenSpec proposal, though the documentation half of it can land immediately.
