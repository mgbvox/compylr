# spec-vs-reality audit evidence

## A. golang-backend spec: error-return contract is entirely absent (panics instead)

Spec text (openspec/specs/golang-backend/spec.md:33): "The backend SHALL emit each function as a Go
function returning `(Ret, error)`". Scenario "Fallible function emission" (line 35-38): `divide(a,b)->int`
"generates `func Divide(a int64, b int64) (int64, error)`". Scenario "Division by zero returns error"
(line 50-52): "the Go helper returns `(0, errors.New("division by zero"))` rather than causing a panic."

Actual run:
```
$ cat /tmp/divtest.ts
function divide(a: number, b: number): number { return a / b; }
$ cargo run -q -p compylr-cli -- --frontend typescript --backend go --emit rust /tmp/divtest.ts
// Code generated by compylr. DO NOT EDIT.
package main

func divide(a int64, b int64) int64 {
	return GoFloorDiv(a, b)
}
```
No `error` in the return type anywhere. crates/compylr-backend-golang/src/emit.rs:118-125 builds `ret_str`
from `go_ty(&function.ret)` alone -- there is no branch that ever appends `, error`.

compat.go (crates/compylr-backend-golang/src/compat.rs:10-25), read from the emitted crate:
```go
func GoFloorDiv(a, b int64) int64 {
	if b == 0 {
		panic("division by zero")
	}
	...
}
func GoRem(a, b int64) int64 {
	if b == 0 {
		panic("division by zero")
	}
	...
}
func GoSubscript[T any](slice []T, index int64) T {
	n := int64(len(slice))
	if index < 0 {
		index += n
	}
	return slice[index]   // no bounds check at all, no error return
}
```
`GoSubscript` has no error return type, no bounds check -- out-of-range indexing is a bare Go runtime
panic ("index out of range"), not the "returns an error if out of bounds" the spec's own scenario (line
46-48) states.

A panic that escapes a `//export`ed cgo function is fatal to the whole host process (documented cgo
behavior) -- this is the mechanism behind the already-filed SIGABRT crash (issue #39), but here it is
tied to the specific spec text that promises the opposite.

Also: class constructors are declared `func NewClassName(...) *ClassName` (crates/compylr-backend-golang/src/emit.rs:47-50),
never `(*ClassName, error)` as golang-backend spec line 33 requires.

## B. golang-backend spec: constructor "initializing fields" is false when param name != attribute name

Repro against the repository's own accepted TypeScript fixture (frontends/typescript/fixtures/accepted/classes.ts):
```ts
export class Accumulator {
    total: number;
    constructor(initial: number) { this.total = initial; }
    add(val: number): void { this.total = this.total + val; }
    get(): number { return this.total; }
}
```
Emitted Go:
```
$ cargo run -q -p compylr-cli -- --frontend typescript --backend go --emit rust frontends/typescript/fixtures/accepted/classes.ts
func NewAccumulator(initial int64) *Accumulator {
	inst := &Accumulator{
		total: 0,
	}
	return inst
}
```
`initial` is never used -- `total` is hardcoded to `0`. Ran it:
```
$ cat /tmp/accver/generated.go   # (bindings.go removed to avoid duplicate main for this scratch check)
func main() {
	a := NewAccumulator(42)
	a.add(8)
	println(a.get())
}
$ cd /tmp/accver && go run .
8
```
Expected `50` (42 + 8); got `8` -- the constructor argument is silently dropped for every case where the
init parameter name differs from the field name. Root cause: crates/compylr-backend-golang/src/emit.rs:38-44
matches `class.init.params.iter().any(|p| p.name == attr.name)` -- pure name-identity match against the
parameter list, never inspecting the actual `self.x = expr` assignments in the constructor body. This is
the repository's own flagship "accepted" class fixture, used to demonstrate class support.

## C. golang-backend spec: tuple type spelling fails `go build`

```ts
function makeTuple(a: number, b: string): [number, string] {
    return [a, b];
}
```
Emitted:
```go
func makeTuple(a int64, b string) struct {
	F0 int64
	F1 string
} {
	return struct {
		F0 int64
		F1 int64
	}{F0: a, F1: b}
}
```
```
$ cd /tmp/goclsout && go build ./...
./generated.go:24:9: cannot use struct{F0 int64; F1 int64}{…} (value of type struct{F0 int64; F1 int64}) as struct{F0 int64; F1 string} value in return statement
./generated.go:27:15: cannot use b (variable of type string) as int64 value in struct literal
```
The literal's field types don't track the declared return type's field types -- this fixture does not
compile at all.

## D. pipeline-architecture spec: "renders the shared conformance corpus" never actually builds Go

Requirement text (openspec/specs/pipeline-architecture/spec.md:163-168): "a backend that cannot render a
corpus entry SHALL fail visibly rather than emitting code that does not build."

crates/compylr-host-python/tests/conformance.rs has, for Rust only:
```rust
/// Rendering is not enough: the result has to build.
///
/// A backend can emit plausible text for a form it does not really support -- that is exactly how
/// tuple indexing once shipped emitting a call to a helper that did not exist. Only handing the
/// output to the target's own compiler settles it.
#[test]
fn every_corpus_entry_compiles_for_the_rust_backend() {
    ... Command::new("rustc") ...
}
```
There is no `every_corpus_entry_compiles_for_the_go_backend`, and:
```
$ grep -rln "compiles_for_the_go_backend\|Command::new(\"go\")" --include="*.rs" .
(no output -- zero matches anywhere in the repo)
```
The only Go-side check, `every_implemented_backend_renders_the_whole_corpus` (conformance.rs:970-989),
calls `backend.emit(&unit)` and asserts non-empty text -- it never invokes `go build`. This is exactly
why finding C (a corpus-shaped tuple return that fails to compile) is not caught by any existing test.

## E. typescript-bindings spec: crate is a version() stub, no requirement is met

crates/compylr-host-typescript/src/lib.rs, in full:
```rust
//! Node-API host extension module for compylr.

use napi_derive::napi;

#[napi]
pub fn version() -> String {
    "0.1.0".to_string()
}
```
Every requirement in openspec/specs/typescript-bindings/spec.md is unmet:
- "Node-API native extension for compylr core" -- only `version()` is exported; nothing else.
- "Expose compiler pipeline operations" (lowerTypeScript, validate/fingerprint, resolve
  frontends/backends/bridges, emit HostArtifacts) -- none of these functions exist.
- "Structured error translation" (LoweringError/FrontendError/BackendError/BridgeError -> JS Error
  with kind/line/column/code/message) -- no error translation code exists at all.

## F. typescript-api spec: no such package exists; the stand-in is a no-op registry

No `initialize`, `.compylr/build.json`, or `COMPYLR_DISABLE` handling exists anywhere in TS/JS source:
```
$ grep -rn "initialize\|COMPYLR_DISABLE\|build.json" demo/demo-ts-go/src/
(no output)
$ find . -iname package.json -not -path "./vendored/*" -not -path "*/node_modules/*" -not -path "./context/*" -not -path "./worktrees/*"
./demo/demo-ts-go/package.json     # only the demo's own package.json; no compylr/@compylr/compylr package anywhere
```
The only implementation of `@compyle`/`compyle()` in the repository, demo/demo-ts-go/src/algorithms/_compylr.ts, in full:
```ts
export class CompylrManager {
    private registered: Map<string, Function> = new Map();
    compyle<T extends Function>(target: T): T {
        if (target.name) { this.registered.set(target.name, target); }
        return target;
    }
    getRegistered(): ReadonlyMap<string, Function> { return this.registered; }
}
export const c = new CompylrManager();
export const compyle = <T extends Function>(fn: T): T => c.compyle(fn);
```
It stores the function in a Map and returns it completely unchanged. None of "Configuration manager
initialization", "@compyle decorator and function wrapper" (source extraction + immediate validation),
"Single shared artifact and first-call compilation" (Go toolchain invocation, FFI load, body
replacement), "Cache validation and fingerprinting" (.compylr/build.json), or "Environment disable
switch" (COMPYLR_DISABLE) exist in any form. (This is the implementation behind already-filed issue #38;
recorded here against the specific typescript-api requirement headings it falsifies, all six
simultaneously.)

## G. typescript-go-bridge: index.js/index.d.ts are emitted for functions the .so never exports

crates/compylr-bridge-typescript-golang/src/bridge.rs: `emit_cgo_function` (line ~71) skips emitting a
cgo export for any function whose params/return aren't in `is_scalar` (Int|Float|Bool|Unit -- note String
is excluded too). But `emit_dts` (line 124) and `emit_js_loader` (line 149) both iterate
`unit.functions()` unconditionally, with no such filter.

Repro:
```ts
function greet(name: string): string { return name; }
function add(a: number, b: number): number { return a + b; }
```
```
$ cat bindings.go
//export Call_add
func Call_add(a C.longlong, b C.longlong) C.longlong { ... }
func main() {}
                                    # note: no Call_greet anywhere

$ cat index.js
const native_add = lib.func('Call_add', 'int64', ['int64', 'int64']);
...
const native_greet = lib.func('Call_greet', 'int64', ['int64']);   # binds to a symbol that was never emitted
function greet(name) { return native_greet(name); }
exports.greet = greet;

$ cat index.d.ts
export function add(a: number, b: number): number;
export function greet(name: number): number;   # `name: string` mistyped as number
```
Verified at the binary level after `go build -buildmode=c-shared`:
```
$ nm -D lib.so | grep -i call_
_Call_add
                                    # Call_greet is not in the binary at all
```
`index.js` unconditionally generates a `lib.func('Call_greet', ...)` binding against a native symbol that
provably does not exist in the compiled artifact -- loading/binding this module would fail (or crash on
first call, depending on the FFI library's binding strategy) for every function whose signature includes
a string, array, map, tuple, or class type -- i.e. most of the accepted corpus. Separately, `emit_dts`
always types every parameter and return as TypeScript `number`, so even a `boolean`-returning scalar
function (`isPos(x: number): boolean`) is declared as `isPos(x: number): number` in `index.d.ts` --
confirmed:
```
$ cat index.d.ts   # for function isPos(x: number): boolean { return x > 0; }
export function isPos(x: number): number;
```
